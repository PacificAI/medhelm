Work reproducibly

{% else %}

Work reproducibly

{% endif %}
  1. Scope one change. Check existing issues. State the workflow, what counts as success, and one failure the evaluation should catch.
  2. Check data access. Use a public or synthetic fixture in the benchmark environment. For a dataset proposal, record the source, license, access conditions, and creator credit.
  3. Pin the inputs. Record code and dataset versions, case IDs, model and deployment, run limits, and any judge and rubric settings. When comparing runs, hold the other inputs fixed, reset any stateful environment, and record whether cached results were used.
  4. Start with one case. Confirm that the scenario loads, the model responds, and the grader writes results. Check setup and judge errors before interpreting any score.
  5. Review the evidence. Compare the model’s response with the grading criteria. For browser tasks, also check the action log and final state. Record execution and judge errors separately from valid scores.
  6. Share the smallest reproducible result. Include the command or scoring rule, a short excerpt that can be shared, and one targeted regression test or assertion. Keep credentials, patient information, and restricted data out of reports and pull requests.

Choose one benchmark. After setup, allow about 15 minutes for HEAD-QA, 30 minutes for HealthBench Professional, or an hour for HealthAdminBench.

HealthAdminBench Browser agent · Two prior-authorization tasks · Requires Chromium and a benchmark portal

Use the HealthAdminBench setup guide to install the harness and run its one-task smoke test. Confirm the portal launches and saves an episode result. The smoke test uses a random agent and may show judge errors if credentials are missing.

From the MedHELM checkout with its virtual environment active, run two synthetic v2 prior-authorization tasks with a configured agent model and a separate judge. Replace the example model and config values. The command assumes the v2 benchmark portal is running locally.

agent_model='provider/model-id'
agent_deployment='provider/deployment-id'
judge_config='path/to/judges.yaml'
portal_url='http://localhost:3002'

tasks='version=v2,task_ids=emr-easy-1+emr-easy-2'
settings="observation_mode=axtree_only,max_steps=20,env_base_url=$portal_url"
models="model=$agent_model,model_deployment=$agent_deployment"
grader="jury_config_path=$judge_config"

medhelm-run \
  --run-entries "health_admin_bench:$tasks,$settings,$models,$grader" \
  --suite collaborator_hab \
  --max-eval-instances 2 \
  --num-threads 1
  1. Record the run. Include the command, MedHELM and HealthAdminBench commits, the portal version, and the agent and judge deployments.
  2. Report each episode. Under benchmark_output/runs/collaborator_hab/, inspect scenario_state.json and per_instance_stats.json. For each task, record points earned and possible, full pass or fail, step count, and any execution or judge error. Flag a judge-error zero as a grading failure when interpreting the output.
  3. Trace one result. Cite one action, portal field, or grader finding behind a score. Distinguish a state-based JMESPath check from an LLM-judged check. Propose one targeted improvement and the assertion you would use to verify it.
HealthBench Professional Two clinician conversations · Physician-written rubrics · LLM judge

Use the MedHELM Quick Start and credentials guide to configure an answering model and a separate judge. Use a judge YAML with one judge and replace the values below with your deployment and config.

Run two HealthBench Professional cases drawn from clinician consultations, documentation, and research. The model answers the final request in each conversation. MedHELM asks the judge to score the rubric items and separately compare the answer with the physician response.

answer_model='provider/model-id'
answer_deployment='provider/deployment-id'
judge_config='path/to/judges.yaml'

answerer="model=$answer_model,model_deployment=$answer_deployment"
grader="jury_config_path=$judge_config"

medhelm-run \
  --run-entries "health_bench_professional:$answerer,$grader" \
  --suite collaborator_healthbench_professional \
  --max-eval-instances 2 \
  --num-threads 1
  1. Record the run. Include the command, MedHELM commit, and model and judge deployments. Under benchmark_output/runs/collaborator_healthbench_professional/, use scenario_state.json and per_instance_stats.json to report each prompt_id and its health_bench_professional_score when grading succeeds.
  2. Review one judgment. Inspect the judge’s saved accuracy.criteria and the case’s extra_data.rubrics. The physician comparison can add a separate entry. If grading fails or results are incomplete, report the failure and apply one rubric criterion manually to an available model answer.
  3. Specify a regression check. Describe a short synthetic request where a useful response would ask for a missing fact or acknowledge uncertainty. State how the judge should score one relevant criterion. Use case IDs and paraphrases to keep source examples out of public reports.
HEAD-QA Five multiple-choice questions · Exact match (EM)

Use the MedHELM Quick Start to run five text questions from the English HEAD-QA test set. Exact match checks the chosen answer against the answer key. The example uses the built-in test model so you can check the scoring pipeline without an API key. Use a configured answering model to assess answer quality.

model_config='model=simple/model1,model_deployment=simple/model1'

medhelm-run \
  --run-entries "head_qa:language=en,$model_config" \
  --suite collaborator_head_qa \
  --max-eval-instances 5 \
  --num-threads 1
  1. Record the run. Include the command, MedHELM commit, and model deployment.
  2. Report only exact match. Under benchmark_output/runs/collaborator_head_qa/, read exact_match in stats.json. Confirm it by dividing the number of correct answers by the number of scored questions in per_instance_stats.json. Report any failed requests separately.
  3. Check one item. Use scenario_state.json to identify one question ID, the model’s output, and the correct choice. Explain its match result.

If setup blocks you, email the failing step and a short, redacted error.

Send your test contribution by email. Include your results in the message or share a link the reviewer can open.

  • Your name, the test you completed, and the requested results.
  • The area you’d like to work on and your approximate availability.
  • Your GitHub handle or a relevant issue, if you have one.

Keep patient information, restricted data, and credentials out of your submission.

Email medhelm@PacificAI.onmicrosoft.com

What happens next

A maintainer checks that they can reproduce your run and that the evidence supports your interpretation of the score. They may ask a follow-up question. If there’s a fit, you’ll agree on one starter issue with a success criterion and get any project access it requires.

Public issues and pull requests are open to everyone. If you’re looking to propose a dataset on behalf of an institution, contact the research team with a short description and its access requirements.
